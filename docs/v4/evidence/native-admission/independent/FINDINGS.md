# Native local-file tool surface: static review

Scope: official `openai/codex` tag `rust-v0.169.0`, read-only source review. No native tool calls, probes, model sessions, candidate execution, permission changes, repository edits, or runtime tests occurred in this review. This does not attest that the installed executable was built from these exact sources.

## Conclusion

`shell_tool=false` alone does **not** close the local filesystem tool surface. `apply_patch` registration depends on model capability, and `view_image` registration depends on its independent feature; neither registration is guarded by the shell-tool setting. Actual exposed tools for the current session remain unverified. This review does **not** establish a permission bypass: both handlers have distinct permission/approval enforcement paths.

## Exact source findings

1. Registration: `core/src/tools/spec_plan.rs:1472` registers ApplyPatch when `model_info.apply_patch_tool_type.is_some()`; line 1486 registers ViewImage when `Feature::ViewImage` is enabled. This source is in the runner's separately indexed official snapshot. Shell registration's early return is separate. Therefore turning off shell does not imply these two tools are disabled.
2. Image reads: `core/src/tools/handlers/view_image.rs:145` resolves the selected environment/path; lines 151, 155, 169 pass that environment's filesystem sandbox context to metadata/read. Image decoding subsequently rejects unsupported/non-image bytes, and image input modality is required. This establishes a conditional **image read surface**, not a general text exfiltration tool or a runtime exploit.
3. Patch writes: `core/src/tools/handlers/apply_patch.rs:492` validates the patch using the filesystem context; lines 515–581 derive effective permissions and approval requirements, then dispatch through the tool orchestrator. `core/src/apply_patch.rs:15` assesses safety and produces autoapprove-with-sandbox, ask-user, or reject outcomes. `core/src/tools/runtimes/apply_patch.rs:90` constructs the context for the actual attempt; lines 180–199 apply through the filesystem backend. These paths do not depend on having a shell tool available. They also do not show unrestricted writes by default.
4. Backend read/write routing: `exec-server/src/local_file_system.rs:91` uses sandboxed reads only when the supplied context says restriction is required; write routing at line 108 is analogous. `file-system/src/lib.rs:395` and 403 implement those predicates as the negation of the permission policy's full-disk read/write access. Thus a context's mere presence does **not** prove A01-style restricted reads; a policy allowing full-disk reads intentionally routes reads directly. Missing configured runtime paths for a required sandbox fails instead of silently falling back.
5. Filesystem helpers: `exec-server/src/fs_sandbox.rs:99` validates paths and materializes permission roots, adds helper runtime read permissions, and forces restricted network policy. Lines 152–204 transform a fixed executable/helper argument under the selected platform policy; sandbox-unavailable returns an error. Lines 350–385 filter inherited helper environment through an allowlist. These source properties do **not** prove protection from other host processes' environment/arguments; previously observed process-info and nested-sandbox limitations are not resolved by this source review.
6. Read-directory/read-file functions exist in the filesystem backend (`exec-server/src/local_file_system.rs:160`, 217), but the reviewed `core/src/tools/handlers/mod.rs` does not register standalone model handlers named `read_file` or `list_dir`. Exact-tag fetches of those guessed core handler filenames returned 404. This is only a bounded source observation: extension/MCP/hosted/code-mode tool exposure and the actual current toolset require separate assessment, not a claim that all other read routes are absent.
