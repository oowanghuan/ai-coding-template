## 已复现及修复

原先的锁与扫描只覆盖一个输出日志目录。旧三适配器测试复用同一执行权/工作区，
却期望三个进程成功退出，不能作为跨供应商防重证据。

新反例实际启动 A，丢弃调用方回执，重建无 owned handle 的控制器观察到
`outcome_unknown`，再用另一个 Adapter、另一个日志目录和不同操作 ID 启动。
两个进程各向原工作区计数文件原子追加一个字节。旧版计数为 **2**，新增反例失败。

修复要求所有绑定显式共享受保护、持久的 `LaunchReservations`，共用文件锁，
先持久化预留再写本地意图和启动。相同 Assignment/workspace ID，或者相同/嵌套
实际目录，均拒绝再次启动。未知结果、进程退出、换 Adapter/操作 ID/token 都
不会清空预留。Registry 拒绝混用预留域；状态/输出依然属于各自绑定，独立绑定
也可共用输出目录。三适配器成功用例改为三份独立执行权及工作区。

这是共同启动约束，不授予权限或替代 Store。不同控制器必须由受信装配固定为同一
预留域；互不共享的域无法互相防重。尚未部署真实 CLI 工厂，也未自动迁移旧日志。
历史未明操作必须先对账，不能新建空域重新执行；绑定/ID格式变化和该限制见
[接口说明](../../../../framework/adapters/README.md)。`writer_stop_confirmed=false`
和工程未验收标记保持；不能凭预留或主进程退出放行接管。
