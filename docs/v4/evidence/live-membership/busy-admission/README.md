## 根因及最小修复

已启用资源池的热登记将新成员 `state=busy` 当成 host 可用，同时无条件设
`stop_confirmed=True`。新身份没有池内 Assignment，`refresh` 因而把它投影为
available。登录和授权有效不能证明这份已忙碌资源仍有可用容量。

在 `lifecycle.admit` 加入明确拒绝：busy 新成员不能登记，即使配置多个 slots。
拒绝发生在同一 Store 事务内，无部分提交，不变更旧任务或停止任何进程。
只有受信控制器随后实际观察到 idle/available 才能重新登记；不能仅改字段
来规避真实忙碌状态。没有新增占用推断、原任务导入、遥测服务或自动空闲探测。
既有成员、额度组、重放与恢复协议保留，范围限于本次热登记。
