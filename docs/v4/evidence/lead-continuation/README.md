# Project Lead 持续推进：候选机制与验证

生产诊断：既有轮询只根据新 Advisor/Owner 事件通知当前会话。无新评论时的
`pending=0` 只说明收件队列为空，不能说明已授权工作没有待办。这是项目协调缺口，
不能从该现象推断某家 Coding Agent 无法持续协作。

联合方案见 [架构 §14](../../V4_ARCHITECTURE.md#14-持续协调方案组织既有-coding-agents)，
有限计划留在原 [工作包账本 §16.2](../../V4_WORK_PACKAGES.md#162-持续推进实践与当前下一步)。
这里只提供候选原型与验证材料；**生产未部署，原生空闲续做未实测，配置默认停用**。
待办投递不代表授予执行权，也不取代工程验收。

候选复用原单锁，读取准确公开版本中的唯一 ready 片段；本地只保存投递、ACK、
已读事件指纹和保护配置。忙碌时不 steer；空闲时检查队列后再投递。未知操作先对账，
未 ACK 不另开激活；ACK 后同任务同公开进度最多两次，远端换批次不能重置本地预算。
新事件变更屏障只要求 Project Lead 对账，不要求 Owner 每步追加授权。没有原生
idle CAS，不能保证读 idle 与入队原子一致；该竞态和停用/期限/恢复边界均写在候选说明。

这不是新 Coding Agent 或新任务引擎，只验证如何让原有 Agent 接着处理已授权工作。
具体依赖已有客户端接口的部分属于 Adapter，不应硬编码进 N 供应商核心 Scheduler。

原始机器记录保留仓库外。公开副本使用通用路径占位，保留原始/公开双哈希；
未发布真实会话 binding、机器 socket、私有实践原件或账号诊断。源文本用于复核，
不作为已经部署或可直接替换生产文件的声明。
