根因是取得真实Popen句柄后，监督器在进入try之前创建选择器、设置管道模式并
注册读事件。线程内初始化异常既不进入内部清理，也不会传播给外层thread.start。
本轮另将线程对象创建和启动纳入取得进程句柄后的异常保护范围。

修复前在选择器创建、第二根管道注册处分别注入异常。每个用例先启动一个真实
固定Python子进程，等待其写出ready标记并核对仍在运行，再触发监督初始化故障。
两次均观察到主进程仍存活、exit_code=null、调用状态running；之后由测试外壳
用自己的准确进程句柄清理。**外壳清理不算产品成功停止**。线程异常栈与两个
失败断言保留，没有把这轮当作通过。

修复后测试五个故障点：选择器创建、第二根管道注册、非阻塞设置、线程构造、
线程启动。每个都实际创建1个固定子进程，产品停止后观察exit_code=-9，状态
outcome_unknown，writer_stop_confirmed=false、engineering_accepted=false。
同操作重放只返回旧调用；新操作ID、替代控制器和执行权释放均拒绝，不新增进程。
缺失完整输出时result拒绝返回“成果”；输出管道关闭、活跃句柄移除都有断言。

实现将初始化置于异常保护内，选择器允许尚未创建。清理分别关闭资源，单个close
失败不跳过其他资源。停止/等待失败仍保留unknown；日志写入失败仍保留原启动
意图，不自动重启、释放或验收。只处理owned主进程，没有按名称杀进程或宣称
全部后代写者停止。完整进程树、最终检查点和一次交付恢复仍待验。
