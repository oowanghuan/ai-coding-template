# V3 → V4 兼容、迁移与回退

版本：0.1，2026-11-26。状态：提案；本轮不执行项目迁移、不删除旧资产。

## 1. 兼容承诺

V3 稳定基线固定为 `8ed245f5a5c7adeebd31b3f31272164ee85a1d39`。V4 新能力先增量落地，旧文档和工具保留；发布物用显式 manifest 选择文件。命令别名、读取兼容和写入兼容分别声明，不能笼统说“兼容 V3”。

| 旧资产 | V4 处理 | 边界 |
|---|---|---|
| Phase 0–7 文档和项目规划 | 保留路径和语义映射，允许按需引用 | 不自动给旧阶段补签认 |
| Feature / PROGRESS_LOG | 一次导入为 WP 草稿及 legacy evidence 引用 | done/passed 缺证据时不自动转 accepted |
| Gate 规则与状态 | 导入规则候选；重算 V4 判定 | 审批用户名字符串不等于身份凭据 |
| Contract Resolver 与扫描 Skills | 保留内容并纳入 canonical 能力源 | 先修断链和验证，再归档旧包装 |
| Claude Commands | 保留兼容别名指向新接口 | 不两套规则双写，不自动推 main |
| `.claude/settings.json` / Hook | 显式检测、提出合并方案 | 不覆盖用户设置，不自动启用 GUI 指令注入 |
| HA Loop Desk | 保留旧 `_gui_config`；未来单向状态投影 | V4 新状态只读，未知字段不猜；GUI 写命令独立验收 |
| `_backup/` | 原仓保留，精简初始化包排除 | 不删除 Git 历史；需要移出仓库时另行批准 |

## 2. 工具源与安装副本的收敛

先为 26 个源命令、6 个源 Skills、5 个源 Subagents 和 15 个仅安装目录 Skills 建立工具 manifest：id、canonical path、版本、内容指纹、依赖、原生加载类型、兼容别名、生成目标。

五个漂移命令逐个对照，不以“源目录必然正确”代替审查。15 个额外 Skills 按用途分类：契约/逆向扫描保留；进度/测试/文档内置逻辑与调用者一起迁移；外部评审改成供应商接口；剩余重复内容在引用闭包验证后归档。Subagents README 声称内置与实际依赖是否一致也要验证。

生成器为可再生入口添加来源和 digest，CI 重生成后比较差异；用户拥有的手改文件采用三方比较，冲突拒绝自动覆盖。供应商入口不成为第二份业务规范。

## 3. 初始化与既有项目接入

接口名称是设计示意，尚不存在可运行的 V4 CLI。

`init/integrate --dry-run` 应输出新增/修改/冲突/不触及文件、目标根、Profile、版本、Git 状态、配置风险及回退清单。dry-run 不写项目文件，不联网、不启动模型、不修改认证或权限。

安全执行顺序：

1. 识别真实 Git 根和 Worktree；保留原 `.git`、remote、分支和全部已有成果。
2. 检查路径穿越、符号链接、大小写冲突、文件所有权、嵌套项目；已存在 AGENTS/CLAUDE/配置文件必须进入冲突处理。
3. 按 manifest 计算计划；优先创建新文件，明确修改范围。所有冲突须有具体差异和选择，不用 `--force` 绕过。
4. 在事务临时目录准备文件，保存原文件字节/权限/指纹及新增文件清单；验证后原子替换，失败回到安装前状态。
5. 写入安装 receipt：版本、manifest digest、transaction_id、before/after hashes、文件所有者、备份位置；秘密不进入公共 receipt。
6. 执行路径/模板/入口/Schema/样例一致性检查；重复执行无额外改动。

空项目可初始化 Git，但不得通过删除已有 `.git` 达到“新项目”效果。接入已有项目先只读扫描，生成目标/技术栈/风险与推荐 Profile；已有业务文件、未提交修改、未追踪文件均保全。逆向结果明确 inferred，未经验证不能获得 signed/accepted 状态。

## 4. 状态迁移与权威切换

迁移前暂停受影响派单，列出活跃 Assignment 和未知结果操作，保存检查点。以固定 SHA 导出旧状态；逐条产生映射报告：可无损映射、需补字段、冲突、无法验证。

- Feature ID 转稳定 WP ID，保存 legacy_ref；同名冲突不合并。
- 旧 phase_5.done → reported implementation completion；不是工程验收。
- 旧 Gate passed → historical assertion；有精确对象及可核证据才允许重建对应里程碑。
- 旧 cc_checkpoint 扩展为新格式；缺未提交资产或执行权信息则标待核，不能启动接管。
- 旧 Owner/approval 字符串保存来源，不自行升级为有效授权。
- 历史日志保留原始字节，转换产物记录输入/输出哈希与转换工具版本。

本地→Team 切换遵循 [架构 §3](V4_ARCHITECTURE.md#3-唯一权威状态源)：freeze、export、validate、切换 authority_epoch、撤旧写者、启新写者。失败时保持旧源权威，不能出现“两个都先写着”。

## 5. 回退

安装回退按 receipt 逆序恢复；只删除“由本次新增且当前哈希仍等于安装后哈希”的文件。用户安装后修改过的文件必须保留并报告冲突，不能强制覆盖。未提交业务改动不执行 reset --hard/clean。

状态回退不等于还原旧文件后重放任务。先停止新执行、对账已发生的外部副作用、导出 V4 新事件；核准旧版本能表达的状态。V4 新字段/里程碑不能无损表达时，只读冻结并人工处理，不假装降级成功。已部署的外部成果必须用对应发布 WP 的回退方案处理。

每个版本维护 schema_version、协议兼容范围及 reader 能力；未知 major 拒绝写入，新增可选字段可读但不得静默丢弃后重写。

## 6. 归档与发布顺序

1. 本轮保留旧资产原位，提交盘点和计划。
2. 经批准修复安装与工具依赖，建立旧项目 fixture 和原生入口发现测试。
3. 先提供 opt-in V4 Alpha；V3 默认入口不被静默替换。
4. 有新建、接入、重复执行、冲突、故障中断和回退实测后才宣布迁移可用。
5. Beta 验证 GitHub 权威切换及并发，再发布 Team 模式。
6. V4 正式发布由 Owner 单独批准。历史归档如果涉及删除或重写历史，提交单独决定；不夹在“整理目录”里执行。

## 7. 必须验证的迁移反例

已有自定义 AGENTS/CLAUDE/settings；脏工作区；未追踪文件；带空格/非 ASCII 路径；符号链接跳出目标；重复安装；升级中断；回退前用户编辑；未知 Schema 版本；两个初始化进程同时运行；旧 passed 没有证据；旧 GUI 读取新状态。验收要求见 [S01/S02/S06/S12](V4_ACCEPTANCE_PLAN.md)。
