# V4 最小闭环与验收计划

版本：0.2，2026-11-28 UTC。**本文件是验收方案及有限证据索引，不是全部产品通过证明。** P0 的 12 项旧版观察与下面 12 个 V4 产品场景不是同一组测试。

## 1. 验收单位和证据

验收对象必须是完整 commit SHA + 候选合入树 + 配置/规范版本，不能只填分支名或 PR 编号。每次记录运行 ID、WP、命令 argv、环境/工具版本、起止时间、退出码、通过/失败/跳过/未测数量、预期用例清单、原始产物及 SHA256、既有失败对比和独立结论。

证据分级：`static_inspection`、`fixture_execution`、`provider_live`、`hosted_live`、`independent_acceptance`。模拟器证明协议行为，不证明供应商认证、加载规则、云端权限或计费可用。作者自测不能替代独立签认。证据真实性和信任边界见 [架构 §7](V4_ARCHITECTURE.md#7-evidence-与可执行-gate)。

所有 fixture 使用合成项目/数据、临时目录和独立 Worktree。故障注入不能作用于 Owner 的真实业务库、认证配置或其他项目。缺环境时记录 blocked/not_run 和理由，禁止用“预计通过”填 passed。

## 2. 最小可运行纵向闭环

空目录 → init Lite → 最小目标及 WP-A/WP-B → 未授权 B 拒绝 → A 获授权/认领 → 隔离目录真实执行 → Runner 捕获证据 → 独立评审准确版本 → 工程验收 → B 的依赖满足后可认领 → 执行中断 → 保全 checkpoint/未提交成果 → 另一 Worker 接管 → 重新验证 → 依据权威 revision 生成进度。

再将同一合成项目迁移到 GitHub backend，在已授权测试资源上运行云/本地竞争及 Advisor 闭环。基础真实 CLI 成功后才增加云端适配；缺云权限时保持 hosted_live 未完成。

计划中的命令接口需由 WP-101/102 确定。这里不提供尚不存在的可执行 `v4` 命令；每个场景实施时把实际调用、测试代码与输出固定到证据包。

### S12-Alpha 的具体用户路径（WP-303 交付证据，不依赖 WP-501）

在空项目或无损接入 fixture 中选择 Lite，给一个低风险文案任务。用户只提供目标、允许修改范围、验收描述（正向要求及不可改变项）；工具从实际项目探测建议检查命令，不能凭空宣称存在测试。运行前呈现范围、风险与拟执行命令；已有明确授权覆盖时直接沿用，否则一次确认。执行、取证、检查点和进度生成由工具完成。结束时用户核对成果和证据，一次结果确认；没有中途风险变化时，最多两次确认，不逐阶段索要审批。

工具生成 wp_id、kind/risk 建议、Git 基线、规范版本引用、执行者/Assignment 元数据、状态 revision、证据/检查点 ID 及测试统计。用户不手填哈希、租约、规范版本或组织角色表；未知值明确显示，不能编造。Lite 默认不要求独立 PMO、Advisor、完整组织图；需要独立验收的高风险任务另按风险提升。

WP-303 保存实际输入、界面/CLI 交互记录、必填字段与确认次数、生成文件清单、命令与产物，以及“低风险任务被意外强制企业流程”和“高风险被 Lite 放过”的负向结果。WP-103 提供初始化/接入能力，WP-303 负责 Alpha 用户路径验收；WP-501 只继承这些记录并补发布包与完整 Profile 覆盖，消除循环依赖。

### A04：机器接入与额度恢复的可执行验收设计

本节承接 [Advisor A04](https://github.com/oowanghuan/ai-coding-template/issues/3#issuecomment-7210718044) 及其链接的产品输入；以下是待实现测试规程，没有新建或运行 V4 调度器。状态均为未执行，具体命令由相应实现包提供并固定版本，不虚构已经存在的 CLI。负责人由现有包承接，未改变实现放行条件。

**共同 fixture。** 一个合成项目，固定代码/策略 SHA，Owner 预先授予一个低风险 WP 的指定角色和路径权限，并设置可观察的项目预算上限；任务先生成内容确定的中间文件，再生成确定的最终文件。记录中间 tracked/dirty/untracked 文件清单和指纹；设置一个无业务副作用的合成外部动作及稳定 operation key。每次重新运行使用独立状态副本，统一记录事件时间、状态 revision、Assignment/fencing、资源组和证据对象；不能通过复用上次“通过”报告完成新场景。

**有界恢复策略。** 优先遵守供应商明确提供且可信的重试时间；时间尚未到不得反复提交模型任务。无重试时间时，项目策略须给出初始间隔、最大间隔、退避/抖动、最大探测次数/截止时间及探测预算。测试 fixture 可固定随机种子和虚拟时钟，例如初始 30 秒、上限 15 分钟、最多 8 次；这些是测试参数，不是宣称适用于每家供应商的官方配额规则。达到上限仍未知则保持 paused/needs_input，不能无限重试或用付费 API 绕过限制。恢复后重新准入，不沿用过期认领；可用状态检查和原子 claim 是两个步骤。

**证据分层与计数。** 模拟器用可控时钟、错误码和额度组证明分类、退避、暂停、排他和重复事件逻辑；真实 CLI 分别记录各适配器实际可观察到的退出/结构化错误和一次真实任务续做。若真实限额/恢复不可控或无权限，不故意消耗额度、不购买新服务，只把真实额度恢复部分记为环境不可用/未测；正常 CLI 调用成功不能替代真实额度恢复证明。机器接入的真实 CLI、第二台物理机器、真实限额恢复、模拟结果分别签认，不能合并为一个 passed。

“自动续做人为干预 0”从系统检测到额度暂停后开始计数，初始接入和范围授权另列；预算/权限/Owner 状态改变导致需要决策不是自动恢复通过用例。恢复延迟分别记录供应商已知恢复时刻（未知则 null）、本机首次观察可用、续做和交付时刻，不捏造精确限额重置时间。“最终交付数 1”按 WP+交付版本统计，并同时记录外部副作用次数，不能靠丢弃重复日志达标。WP-303 汇总 Alpha 证据；WP-403 汇总 Team 物理跨机和真实并发证据；所有场景的独立验收仍按风险要求执行。

## 4. 风险增强用例

并发/幂等核心选择属性测试和小状态空间模型；权限边界选择隔离及否定权限测试；迁移选择正反向和失败恢复；关键验收逻辑选择变异测试验证测试是否真能发现错误。每项由风险评估决定，普通文案只运行相应一致性/链接检查。

故障矩阵至少覆盖：进程开始前、认领后未执行、执行中、提交前后、签认后变化、外部动作完成但 receipt 丢失、接管后旧进程恢复。每个断点明确状态、保留资产及下一步允许动作。
