## 1. 产品目标

**Build AI-native Engineering Organizations.**

让目标、职责、授权、工作状态和工程证据在模型、会话与设备更换后仍然有效。V4 提供研发组织协议、可执行的最小工具链和供应商适配；继承 V3 的规划、Feature 工作流、质量关卡、契约解析及恢复经验。

产品形态：**Multi-provider, Model-agnostic Engineering Resource Pool**。
Owner 明确：依托现有 Coding Agent 供应商的能力，组织和协调它们形成持续交付的研发组织。
推理、代码编辑、原生工具、模型路由和原生 Session 由既有 Agent 产品提供；V4 优先使用
它们支持的 CLI、SDK、项目指令和授权机制。V4 负责跨执行者的任务、责任、授权、资源
匹配、交付证据、独立验收与安全接续，不自行训练或调优一个新的 Coding Agent，
也不重做供应商已有的模型执行循环和工具平台。

本项目由 Owner 直接管理，不调动其他项目的 PMO、研发会话或基础设施。当前已批准
批次包括 [OD-09](OWNER_DECISIONS.md#od-09本地-lite-alpha-实现与限定依赖采纳)
的 WP-301/302/303。独立分支和 Draft PR 交付保持；重大架构改变、发布和新增费用
仍须另行裁定。Owner 提供的在用协作实践作为优先设计输入，公开材料只保留通用机制，
不复制私有业务、原始台账、任务标识或机器配置。

## 3. 六项原则

1. **Model-agnostic**：Role、Worker、Provider、Host、Session、Work Package、Assignment 分开建模。组织规则只有一份，供应商入口只引用它。
2. **Evidence-driven**：已提交、已评审、已合入、工程验收、部署和业务验证具有不同语义。自报结果只能作为待验证材料。
3. **Recoverable**：持续检查点、原始成果保全、未知操作对账、认领代次与版本核对先于接管。
4. **Governed**：先有明确范围与权限，再启动执行。Lite 也不能降低高风险任务的安全底线。
5. **Autonomous**：授权范围内自动推进；对真正的范围、成本、权限和业务选择请求裁定。批准规划不自动批准执行。
6. **Asset-oriented**：把可复用能力、交互、判断、工作流、评测和经验登记为资产；经验先验证再升级为规范。

## 4. 最小可用版本与批次调整

建议先交付 **V4 Alpha：本地闭环 + 两个 CLI 适配**，随后交付 **Team Beta：GitHub 权威协调与 Advisor 闭环**。

持续协调必须进入 Alpha 的实际使用路径：有合格资源和已授权待办时能够继续推进，
不依赖 Owner 或 Advisor 再发一条消息。确定性巡检与专业 PMO 判断分离；资源不足、
认证失败、权限不足、未知操作或预算限制时，明确阻塞受影响动作，其他任务继续。
先复用现有调度和 Agent 能力验证，暂不建设完整分布式调度平台。

Alpha 必须能初始化空项目、无损接入既有项目；用同一工作包协议进行授权检查、依赖判断和排他认领；在独立 Worktree 中执行；捕获真实测试产物；由独立评审者针对准确版本评审；中断后可以换供应商接管；生成可重建的工程进度。

Alpha 不宣称无人值守、云端集成或 Enterprise 已完成。两家真实 CLI 的联合验收没有完成时，只能称为协议原型，不能称为多供应商 Alpha 通过。

调整原 P0–P5 顺序的原因：证据验证和最小安装必须进入首个纵向闭环，不能先做完全部角色/规范再验证安装与执行；Github 并发基础须在自动派单之前验证；长期资产和高级风险工具采用插件式增强，避免先建设一个平台再验证产品需求。

## 5. 三个 Profile，共用一个核心

| 项目 | Lite | Team | Enterprise |
|---|---|---|---|
| 权威运行状态 | 单机 Git 状态账本 | GitHub 单一任务权威；Issue 优先试点与控制分支方案待 OD-02 定案 | 沿用选定 Team 后端，按风险增强 |
| 必要组织 | Owner/实现者可兼任 | Owner、协调职责、Workers、独立 Reviewer | 按风险增加独立验收、治理、安全职责 |
| 默认流程 | 目标、WP、检查点、构建/测试、风险判定 | 加认领、依赖、独立评审、共享状态 | 加跨契约、职责隔离和高风险门禁 |
| Advisor | 不要求 | 可选 | 按需配置，不自动成为审批人 |
| 文档成本 | 最小配置和单个 WP，可由工具生成 | 结构化任务与证据 | 只增加有实际控制目的的记录 |

Profile 只决定默认值，最终要求为 `max(profile_floor, task_risk_floor)`。普通文案无需部署、变异测试或形式化检查；权限、资金、敏感数据、破坏性迁移无论 Profile 均提升风险等级。

## 6. 非目标与反对意见

- 第一版不建设通用 Agent Runtime、远程设备管理平台、消息总线、六套资产引擎或新的 GUI。
- 不训练基础模型、不构建新的 Coding Agent 推理/编辑引擎，不把每次供应商原生升级都变成核心协议重写。
- 不把八阶段变成所有任务的强制流水线。Phase 用于描述方法；交付状态由证据定义。
- 不把每条 Advisor 意见都变成新工作包或审批点。优先挂到已有 WP，允许有证据的不采纳。
- 不以不同模型名称证明独立性；必须核对实际作者、评审身份、执行上下文和写权限。
- 不把哈希当作测试真实性证明。哈希证明内容一致；执行真实性还需要受控 Runner、可核对的执行记录及独立复跑。
- 不承诺用 GitHub Issue 评论“先查后写”就能实现严格排他。唯一写入责任、执行权排他或必要的原子更新未验证时，自动竞争认领与切主保持关闭；可先采用受控人工单写协调，不强迫该试点先建设控制分支。
- 不直接删除旧 Skills、GUI 资产或历史文件。重复入口经语义核对后才生成映射与归档方案。
- 不为个人项目强制完整组织图、长期 PMO/Advisor 或六类资产报表。

这些取舍来自旧版安装故障、源副本漂移、Prompt 编排与真实执行的边界，以及本次明确要求的风险控制，并非否定旧框架。

## 7. 成功度量

首批成功标准以 [验收计划](V4_ACCEPTANCE_PLAN.md) 的 12 个场景及负向用例为准。记录测试对象、环境、命令、退出码、用例数量、原始日志、证据指纹和复核结论。

研发度量分别呈现：计划/已交付/已评审/已合入/已工程验收/已部署/已业务验证数量；阻塞时长、首次验收通过率、接管耗时、重复派单次数、未决未知操作数，以及真实复用次数。PR 数量、文档页数、规范签认数量不能替代产品完成度。额度和成本未知时明确写 unknown，不估造数字。

组织能力另测：新 Agent 从登记到首个受控任务的耗时、有 Ready 工作但资源闲置的时间、
提交到独立验收的等待时间、无需人工提醒而推进的次数，以及更换模型/机器后任务与
责任是否保留。轮询次数、`pending=0`、收到通知或 Agent 回复本身都不是交付进展。

## 8. 研发与公开边界

只在独立分支开发，不直接推送 main；不重写 V3 历史。公开交付只包含公开基线事实、通用协议及合成示例。私有研究原件、链接、业务名称、内部授权和完整评审记录留在仓库外。发布前检查新增文件、提交历史和日志；真实秘密不得靠简单遮罩后继续保存在 Git 历史。

本轮公开交付是待评审提案。Owner 采纳提案、批准实现批次、批准公开发布是三种不同事件，须分别记录。
