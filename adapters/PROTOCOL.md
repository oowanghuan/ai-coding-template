# Provider adapter boundary

The shared task, lease, checkpoint, evidence and governance protocols remain authoritative. These adapters do not create another task system, release modification rights, approve a delivery or retry a request. Provider roles are replaceable resources, not persistent authority.

`framework.adapters.classify_result` is a bounded, deterministic parser. The caller supplies the actual observed exit and a protected provenance label; an output field claiming `provider_protocol` cannot grant that label. `synthetic_fixture` records exercise protocol rules but establish no live integration. Raw stdout, free-text errors and model-generated JSON are untrusted by default. The parser returns `kind`, `retry_at`, `provider`, `observed` and `evidence_level`. Unknown reset times remain null; no timezone, interval or account-credit assumption is made.

Limit categories stay distinct: rate limits may have a documented reset, quota may require account action, context exhaustion needs checkpoint/replanning, authentication needs authorized reauthentication, and a local execution budget is not a provider quota. `observed.budget_scope` distinguishes invocation/session limits; neither authorizes changing project budget state. A supervisor budget event without a separately bound scope remains `supervisor_unspecified`. A maximum-turns stop is an invocation error, not budget exhaustion. No category authorizes buying credits, changing accounts, copying credentials or disabling protection. `observed.process_exited` must remain false until actual termination is known; an internal provider retry is not a stopped worker. Scheduling and lease decisions belong to the trusted lifecycle controller, which must reconcile protected checkpoints and unknown outcomes before handing work over.

`build_run_spec` creates a **non-executable proposal**, always `execution_authorized: false`. It bounds prompt, time and output and does not accept arbitrary commands, paths, environment or permission settings. Its argv templates are documentary starting points, not reviewed launcher capabilities. The launcher must independently pin the exact vendor binary/configuration and validate every enabled tool, hook, MCP, plugin, managed customization, credential and network boundary before execution. Codex read-only is not tool-free. Claude safe-mode still applies managed policy. Successful process exit is not engineering acceptance.

`parse_proposal` accepts only `{baseline_sha, files:[{path,old_sha256,content}]}` under a protected assignment's exact old hashes and allowed paths. It returns data, performs no writes and executes no patch or command. The eventual apply stage must independently recheck the active lease, baseline, current file hashes, path/link safety and conflicts. Changed code must receive real tests and independent review.

`render_entries` produces identical AGENTS.md and CLAUDE.md wrappers for one project-root-relative rules source and SHA256. It does not install or overwrite files. The examples beside this document share this source; they do not maintain separate provider business rules.

## N-provider registration

`AdapterRegistry` is the provider-neutral boundary. Reviewed application wiring explicitly registers a descriptor and planner/classifier callables; it never loads module paths from JSON or model output. Unknown adapters and duplicate registrations fail closed. Built-in Claude/Codex functions remain concrete adapters, not an exhaustive list in the lifecycle core.

Each descriptor separates `agent_tool`, `model_provider`, `model`, opaque `credential_ref` and `quota_group`, plus adapter identity. No credential bytes belong in this data. The twelve capabilities (`auth`, `availability`, `start`, `status`, `stop`, `result`, `quota`, `recovery`, `checkpoint`, `native_resume`, `logs`, `evidence`) use `supported`, `unsupported` or `unknown`; omission and booleans are invalid. These declarations describe this integration, not all capabilities marketed by a vendor. Present concrete adapters support result parsing but have no approved live start operation.

The registry includes a third `synthetic-fixture` adapter. Its plan/result shapes match other adapters and its classification evidence is always `synthetic_fixture`. It can exercise the independent lifecycle/runner without claiming a real provider. Adding another explicitly registered adapter does not change task or lifecycle code. Descriptors are protected configuration assumptions; a self-declared model output cannot establish a provider identity or promote unknown capability to supported.
